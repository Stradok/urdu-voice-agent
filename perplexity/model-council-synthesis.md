# Model Council Synthesis — Choosing the LLM stack for a voice customer-support agent

Council: **Claude Opus 5**, **GPT 5.6 Sol**, **Gemini 3.1 Pro**. Question: which models to use for a Pakistan-based voice support agent that talks to customers, books appointments, confirms with doctors, checks inventory, dispatches deliveries, verifies products from photos, finds products from photos, and runs RAG with embeddings + reranking.

Note: the GitHub repo you linked (`Stradok/Idea_vault`) only contains a default Flutter README, so all three models worked from your written description.

## Comprehensive Analysis

The council converged strongly on the shape of the system even while disagreeing on the components, and that convergence is the most reliable signal here. All three models independently rejected the intuitive design — one big smart model that talks, sees, searches and acts — in favor of a **two-plane architecture**: a fast, cheap conversational model with a small number of narrowly scoped read-only tools handling the live call, and a separate, slower, stronger model handling writes and messy multi-step work off the audio loop. GPT 5.6 Sol gave the sharpest technical justification: OpenAI's realtime model does not support Structured Outputs while the GPT-5.6 text models do, so schema-validated bookings and shipments physically cannot be produced by the model doing the talking. Claude Opus 5 arrived at the same split from a different direction, arguing that solo builders who hang 25 tools off a realtime model get both bad latency and bad reliability. Treat this as settled: your conversational LLM choice is a swappable, low-stakes decision, and your action-execution layer is where the engineering should go.

The council also unanimously told you **not to build a computer-use agent**. "Find me this mouse from a photo" reads like browser automation and almost never is. The correct escalation ladder is your own catalog index → supplier feeds and product APIs → a grounded web-search call → and only then a GUI agent, sandboxed, with a hard step cap, running asynchronously. Gemini 3.1 Pro added the specific failure mode: pixel-based clicking hallucinates and loops, so if you ever do need it, use DOM/accessibility-snapshot tooling like the open-source `browser-use` library rather than pure vision. Similarly, all three agreed a reranker is the highest-ROI dollar in your retrieval stack, and that Jina CLIP v2 is the sensible open-weight multimodal embedding default.

The **most important disagreement is speech-to-speech versus a modular pipeline**, and I'd weight it toward Claude Opus 5's position, because it is the only report that verified vendor language tables line by line rather than trusting marketing copy. Gemini 3.1 Pro asserted that Gemini Live has strong native Urdu grounding; Opus 5 found that Google's own Live API docs list `ur` among 97 languages while the Vertex native-audio voice table omits Urdu entirely, and that ElevenLabs' fast, cheap Flash v2.5 and Multilingual v2 models exclude Urdu — only the pricier Eleven v3 supports it. It also surfaced that Deepgram Nova-2 scores 100% WER on Urdu FLEURS while ElevenLabs Scribe scores 3.1% on the same set. That bimodality is the decisive argument: in Urdu, providers don't degrade gracefully, they fail completely and unpredictably, so you need to be able to swap one box without rebuilding the agent. Native speech-to-speech welds STT, reasoning and TTS into one non-substitutable unit. Gemini 3.1 Pro's counterargument about VAD failing at code-switch boundaries is real and you should mitigate it explicitly with semantic turn detection rather than volume thresholds — but it is a solvable engineering problem, whereas "your TTS cannot speak Urdu" is not.

The **embedding-space disagreement** is genuinely unresolved and cheap to test yourself. Opus 5 wants two indexes (image→image, text→text) fused and reranked, citing measured modality gaps across models; Sol wants one aligned Voyage multimodal space fused with BM25 and exact-SKU lexical matching. Build the lexical + text path first — most "find me this mouse" queries are actually resolvable from brand, colour and form-factor text — then measure whether a separate image index beats a unified one on your own catalog. What is not optional, and what only Opus 5 flagged, is that **off-the-shelf visual embeddings are not good enough for SKU-level matching**: 41% top-1 untuned versus 89% after top-tuning a small head on frozen features. Budget for collecting a few thousand of your own product photos.

Two things the council surfaced that fall outside your question but will hurt more than a wrong model pick. First, **telephony economics**: Twilio bills $0.155–0.18/min to Pakistani numbers versus $0.004/min for WebRTC, meaning the phone line costs several times your entire AI stack. WhatsApp Business Calling charges nothing for user-initiated calls and is the natural primary channel in your market. Second, **Pakistan's data-localisation trajectory** — the draft PDPB and the National Data Governance Policy 2026 point toward in-country hosting requirements for sensitive personal data, and doctor-appointment data is exactly the category most likely to be captured. Keep PII and call recordings on infrastructure you can relocate, and send only minimised payloads to foreign model APIs.

**My recommendation.** Start with a modular pipeline: **ElevenLabs Scribe v2 Realtime** for STT, **Gemini 3.5 Flash** as the in-call conversational and tool-calling model, and **ElevenLabs Eleven v3** or **Sarvam Bulbul V3** for TTS — with a hard requirement that you A/B them on 200–500 real Urdu/Roman-Urdu/Hinglish utterances before committing, scoring **slot error rate** on names, dates, addresses, phone numbers and SKUs rather than WER. Put every write behind a **GPT-5.6-class or Claude-class action model with strict JSON schemas, idempotency keys, spoken read-back confirmation, and human-in-the-loop for the doctor confirmation**. Run retrieval as BM25 + text embeddings + a Voyage or BGE reranker, with a VLM adjudication pass over the top 3–8 candidates that is always allowed to answer "uncertain". Keep native speech-to-speech behind a feature flag for English-dominant callers, where it is genuinely cheaper and feels better. And take Opus 5's parting advice seriously: **ship the WhatsApp text agent first** with the same tools, same RAG and same schemas — it costs a fraction, has no latency budget, and lets you make the write path boring before you add voice on top.
